# Decision Log from Separate Project

Contains information on how to fix AppImages

## 2026-07-10: AppImage Segfault After System Crypto Library Updates

* **What was decided**: In `src-tauri/src/lib.rs::run()`, before `tauri::Builder::default()` is constructed, unconditionally set both `GIO_MODULE_DIR` and `GIO_EXTRA_MODULES` to a nonexistent path on Linux, disabling GIO's extension-module scanning entirely for this app.
* **Why**: The AppImage crashed (SIGSEGV) on every launch after a routine CachyOS package update. Root-caused via `coredumpctl`/`gdb`: GTK's very first CSS provider load (during main window creation) triggers `g_vfs_get_default()`, which does a one-time scan-and-`dlopen`-everything pass over GIO's module directories (this is how GIO's extension-point system works - not lazy per-module, it loads the whole directory on first VFS use). Two module directories get scanned: the host's compiled-in default (e.g. `/usr/lib/gio/modules/`) and `GIO_EXTRA_MODULES` (set by the AppImage's own linuxdeploy-generated `AppRun` hook to the app's bundled `usr/lib/gio/modules/`, containing a bundled `libgiognutls.so`). Checksum comparison proved the AppImage's bundled `nettle`/`hogweed`/`gnutls`/`p11-kit`/`leancrypto` do not match what's currently installed on the host, even immediately after a fresh `npm run tauri build` - and critically, `libgmp` (which those crypto libs also need) is *not* bundled at all, so it's always resolved live from the host. When the bundled (stale) crypto stack combines with the host's current `libgmp`, the two are ABI-incompatible and it segfaults inside `dlopen`. Reproduced deterministically and isolated to this exact mechanism with a standalone `ctypes.CDLL(...)` load of `libgiognutls.so` under the AppImage's `LD_LIBRARY_PATH` (crashed), versus the same load with a normal environment (succeeded). This app has no use for any GIO extension point (TLS backend, dconf settings, proxy resolvers, gvfs) - all networking goes through `reqwest` in the Rust backend, and the webview only ever loads local bundled content - so disabling module scanning outright has no functional downside. Same underlying class of bug as the 2026-06-26 "AppImage URL Opening Fix" entry above: the AppImage's `LD_LIBRARY_PATH` override leaking into code paths that dynamically load libraries the bundler didn't fully control.
* **What was rejected and why**:
  - *Deleting/regenerating `hidden-gems.AppDir` before each build*: tried first (hypothesizing linuxdeploy incrementally reuses a stale cache directory and skips re-copying already-present files) - checksums of the bundled crypto libs against the host were still different after a full clean rebuild, disproving this theory. Not a viable fix; not pursued further once the true mechanism (module-scan `dlopen` of an ABI-mismatched stack) was confirmed directly.
  - *Only overriding `GIO_MODULE_DIR` (the host default directory)*: tried first, appeared to work in one manual test run, but a coredump still occurred moments later on a repeat run - the crash was actually coming through `GIO_EXTRA_MODULES` (the AppImage's own bundled module directory), not just the host's default. Both env vars need to be disabled together.
  - *Patching the generated `AppRun`/`apprun-hooks/linuxdeploy-plugin-gtk.sh` inside the built AppImage directly*: rejected - those files are build artifacts regenerated by linuxdeploy on every `tauri build`, so a hand-edit would be silently lost on the next build. Fixed in Rust source instead so it survives every future build, same rationale as the earlier `open_in_browser` command.
